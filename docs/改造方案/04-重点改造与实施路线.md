# 第一部分 · 三项重点改造

## 1. 宿舍分布：把「容量寄生在记录上」改成正式的房间模型

### 1.1 现状为什么必然出错

现状是「一条记录 = 一个床位」，容量没有地方放，只能寄存在**该房间数组顺序第一条记录**上（`L13685`）：

```
cap = 该房间记录列表.map(x => Number(x.capacity)).find(v => v > 0) || 8
```

这一行同时踩了四个坑：种子数据里**根本没有 `capacity` 字段**（`L2539`）；`.find` 取的是数组顺序第一个而非用户最后设置的那个，而 `DB.add` 一律 `unshift` 到头部（`L3330`），顺序会漂移；写容量时要靠 `building|room` 字符串拼 key 反查记录，拼不上就**静默不写却提示成功**；改容量用 `window.prompt()`（`L13824`），在 CEF/Electron 外壳里常被禁用或直接抛异常。再加上床号是自由文本（「1号床」/「1」/「01」/「靠窗」），去重后重复或为 0，满员误判、记录从卡片视图消失（`L13689`、`L13645`）。这不是一个可以「修一修」的实现，是数据模型错了。

> **验证状态说明**：前三条已由代码确认（种子无 `capacity`、`.find` 取首值、字符串拼 key 未命中仍提示成功）。第 4 条（`prompt()` 在 exe 外壳中抛异常）是**依据宿主环境的常见行为推断的**，未在本机 exe 中复现。实机验证方法：复现报错时打开 F12 控制台看 `[全局错误兜底]`（`L17925`）打印的原始消息，或看 toast 原文是否形如 `出错了：prompt() …`。即便这条不成立，前三条也足以解释「配置没生效」；而 `prompt()` 换成应用内模态框本来就是必须做的改动。

### 1.2 新模型

```
dorm_room                           dorm_bed
─────────────────────────           ──────────────────────────────
id            PK                    id           PK
building      TEXT  NOT NULL        room_id      FK → dorm_room.id  (ON DELETE CASCADE)
room_no       TEXT  NOT NULL        bed_no       INTEGER NOT NULL   -- 1,2,3…
capacity      INTEGER NOT NULL      student_id   FK → student.id NULL UNIQUE
              DEFAULT 8             is_head      BOOLEAN DEFAULT 0
note          TEXT                  note         TEXT
UNIQUE(building, room_no)           UNIQUE(room_id, bed_no)
```

- **容量是房间的属性**，改一次就落库一次，不存在「设置成功但没生效」。
- `(room_id, bed_no)` 唯一 → 重复床位在数据库层被拒绝，返回明确的错误码 `DORM_BED_DUPLICATE`。
- `student_id` 唯一 → 一人一床，换床就是改这一列。
- 显示时统一格式化为「N 号床」，导入时把「1号床 / 01 / ①」归一化为整数，**解析不了的行进冲突报告**，不再静默丢进 extra 区。
- 房间存在与否由外键保证，宿舍值日不可能再引用一个不存在的房间。

### 1.3 交互改造

| 场景 | 现状 | 改造后 |
|---|---|---|
| 改容量 | `window.prompt()` | 应用内模态框，数字输入 + 上下限（1–32）+ 实时校验；容量调小时提示「当前有 N 人，调小到 M 会导致 X 人无床位」，需二次确认并列出待调整名单 |
| 加人 | 点空格子预填床号，用 `\|` 拼接字符串传参 | 点格子 → 打开学生选择器（带搜索、排除已有床位的学生）→ 提交 `/api/v1/dorms/beds/{bedId}/assign` |
| 满员提示 | toast 一句「该宿舍已满」 | 满员房间在界面上有明确标记，且给出「调整容量 / 换房间 / 查看未分配名单」三个出口 |
| 找床 | 无 | 新增「**未分配住宿生**」视图与「**空床位**」视图；顶部显示「已分配 N / M，未分配 K」 |
| 报错 | `出错了：Cannot read properties of undefined` | 结构化错误：`{code, message, detail}`，例如 `DORM_ROOM_NOT_FOUND` → 「该房间已被删除，列表已刷新」，并自动刷新列表 |

### 1.4 错误码清单（宿舍域）

| code | 触发 | 前端提示 |
|---|---|---|
| `DORM_ROOM_NOT_FOUND` | 房间不存在/已删 | 该房间已被删除，已为你刷新列表 |
| `DORM_BED_NOT_FOUND` | 床位不存在 | 该床位已不存在，已为你刷新列表 |
| `DORM_BED_DUPLICATE` | 床位号重复 | 该房间已有 N 号床，请换一个床号 |
| `DORM_BED_TAKEN` | 床位已有人 | 该床位已分配给「张*」，请先移出 |
| `DORM_STUDENT_ALREADY_ASSIGNED` | 该生已有床位 | 「张*」已在 3 楼 302 室 5 号床，是否改为换床？ |
| `DORM_CAPACITY_TOO_SMALL` | 容量小于当前占用 | 该房间现有 N 人，容量不能小于 N |
| `DORM_CAPACITY_RANGE` | 容量超范围 | 容量需在 1–32 之间 |

### 1.5 迁移注意

从旧的 `dorms` 记录聚合房间时，`capacity` 只能靠推断：取该房间所有记录里**非零的最大值**，全为 0 或缺失则默认 8，**并在迁移报告中逐房间列出**「推断容量」与「来源」，让用户确认一遍。这一条必须做，否则用户「设过的容量」会以推断值的形式静默丢失。

## 2. 作业提交率：从手填改为计算，并统一三套口径

### 2.1 现状的三套口径

| 口径 | 位置 | 数据来源 |
|---|---|---|
| 提交率百分比 | `homework.rate`（`:11919`，默认 100） | **用户手填** |
| 欠交频次榜 | `homework.unsubmitted` 自由文本按顿号拆分（`:11949`） | 用户手填的名单 |
| 学生档案「欠交 N 次」 | 该生姓名在 `unsubmitted` 文本中出现次数（`:8826`） | 同上 |
| 首页「作业待收」 | `h.submitted < h.total`（`:7011`） | **字段不存在，恒为 0** |
| 课程作业提交率 | `courses[].homework[].rate`（`:14689`） | 另一份手填值 |

五处互不相通。

### 2.2 新口径（唯一实现）

放在 `services/homework_rate.py`：

```
输入：total（应交人数）、unsubmitted_student_ids（未交学生集合）
输出：
    if total <= 0:                 rate = None   # 不显示百分比，显示「—」
    else:                          rate = round((total - len(未交且在本班名单内的学生)) / total * 100)
```

约定与边界：

- `total` 默认取当前班级学生数（快照到记录上，避免后续转学导致历史数据变化）；可手动改（例如只统计走读生）。
- 未交名单**关联 `student_id`**，不再自由文本；同一学生重复选择自动去重。
- 未交名单里出现不在本班名单的学生 → 拒绝并提示（避免「张三 」带空格这种脏数据混过）。
- 计算结果写入 `homework.rate_calc`；`rate_mode = 'auto' | 'manual'`，`rate_manual` 仅在 manual 模式使用。界面在手动模式下明确标注「手动覆盖」，并显示自动值供对比。
- **一致性校验**：保存时若 `rate_mode='manual'` 且 |手动值 − 自动值| > 5，提示「手动值与未交名单推算值差异较大（手动 85% / 推算 62%），确认保留手动值？」

### 2.3 界面变化（这是本轮唯一改版的字段）

| 位置 | 现状 | 改造后 |
|---|---|---|
| 作业表单 | 一个「提交率（%）」数字输入框，默认 100 | 显示「**应交 N 人**」+「**未交名单**（学生多选）」+ 实时预览「**提交率 62%**（自动计算）」；另有一个折叠的「手动覆盖」开关 |
| 作业列表 | 手填值出进度条 | 计算值出进度条，附「未交 5 人」可点开看名单 |
| 学生档案 | 「欠交 N 次 / 共 M 次作业」 | 同样口径，但改为读计算结果 + 未交关联，不再做文本匹配 |
| 首页「作业待收」 | 恒 0 | 「今日应交 N 份，已收 M 份」→ 未交即 `未交学生数 > 0` 的作业数 |
| 课程作业 | 独立手填 | 合并到同一张表（`course_id` 可空），同一套计算 |

### 2.4 迁移

现有数据的 `rate` 是手填值，`unsubmitted` 是文本。迁移时：

- 保留原 `rate` 到 `rate_manual`，`rate_mode` 设为 `'manual'`（**不擅自改用户的历史数据**）。
- `unsubmitted` 文本按顿号拆分 → 姓名匹配学生（`sno` 优先，姓名兜底，同名进冲突报告）→ 写入 `homework_unsubmitted`。
- 报告中列出「手填 `rate`」与「未交名单推算值」差异 > 10 个百分点的记录，供用户决定是否切换为自动模式。
- 提供一键操作：「全部作业改为自动计算」，执行前展示将变化的记录清单。

## 3. 媒体留档：照片与录音

### 3.1 现状

只有图片，且以 base64 data URL 存在那一个 localStorage 键里（头像 240px、多图 1200px、JPEG 0.82）；全应用**没有录音能力**（无 `MediaRecorder` / `getUserMedia` / `capture=`）；设置页的占用条按 5 MB 估算（`:16711`），早已是隐患。另有字段错配：种子数据是 `meetings.photo` / `events.photo`，页面实际写的是 `images`（班会）或干脆没有照片字段（大事记）。

### 3.2 存储设计

```
data/
├── workbench.sqlite
├── media/
│   ├── 2026/09/<uuid>.jpg          # 原件（保持原始像素）
│   ├── 2026/09/<uuid>.m4a          # 录音原件
│   └── thumbs/<uuid>_320.jpg       # 缩略图（图片）
└── trash/<date>/…                  # 删除回收站
```

`media` 表：`id, owner_table, owner_id, kind(image|audio|video|doc), filename, rel_path, mime, size_bytes, width, height, duration_ms, sha256, sort_order, created_at, deleted_at`。

- 图片：保留原件，另生成 320 / 1200 两档缩略图；读取 EXIF 方向并自动旋转（现状未处理）。
- 音频：记录时长、采样率、编码；页内 `<audio controls>` 直接播放，不转码（避免引入 ffmpeg 依赖；若后续要转写再评估）。
- 去重：按 `sha256` 判断，重复上传直接复用已有文件。
- 大小限制：单文件默认 50 MB（图片 / 录音各自可配）；超限返回 `MEDIA_TOO_LARGE`。
- 占用统计：`/api/v1/settings/storage` 真实遍历目录，分项显示「数据库 / 图片 / 音频 / 回收站」（备份功能推迟，不列此项）。

### 3.3 音频归档（**不在本项目内录音**）

**用户已确认：录音由教师自己用手机打电话时录制，本项目只负责归档。** 因此原方案里最难做兼容、也最容易引发争议的一环被整个去掉了：

- **不做**浏览器录音：不引入 `MediaRecorder` / `getUserMedia`，不需要麦克风权限，不做格式兼容矩阵。
- 教师把手机录音文件（`m4a` / `mp3` / `amr` / `aac` / `wav`）通过 `<input type="file" accept="audio/*">` 或拖入页面**上传归档**。
- **播放兼容要留意**：部分安卓录音格式（`amr`、`aac`）浏览器可能不能直接播放。后端读元数据时识别编码，遇到播不了的格式在列表里标注「需下载后播放」并提供下载按钮（**不做服务端转码**，避免引入 ffmpeg 依赖）。
- 归档时填写：关联学生、沟通日期、沟通方式、备注；**时长与编码由后端读取**，不靠用户填。
- 音频只归档、不索引内容。后续若要转写，接本地 FunASR 是可行的增强项（团队已有该环境，目标机也不再有 32 位限制），但**不在本轮**。

### 3.4 可挂附件的记录

| 模块 | 附件类型 | 对应需求 |
|---|---|---|
| 家长联系日志 `contacts` | 照片 + 音频归档 | 用户明确要求「和家长沟通之后留档」 |
| 家访记录 `visits` | 照片 | 家访留痕 |
| 学生谈话 `talks` | 照片 + 音频归档 | 违纪谈话留痕 |
| 主题班会 `meetings` | 照片（多张） | 班会留痕 + 现场照 |
| 班级活动 `classact` | 照片（多张） | 班级相册 |
| 班级大事记 `events` | 照片 | 荣誉/竞赛留证 |
| 矛盾调解 `conflicts` | 照片 | 调解协议/现场 |
| 学生本人 | 头像 1 张 | 现有能力 |

统一用 `media-picker`（选文件 / 拍照上传 / 排序）与 `media-viewer`（灯箱 / 音频播放器）两个组件，各页只声明「本页支持哪些 kind」。

### 3.5 留存与合规（写进产品界面，不只是文档）

录音是教师在校外自行完成的，本项目不触发录制，因此界面提示的重点是**谁能看到、留多久**：

> 归档的照片与录音存放在**你自己的电脑上**，不会上传到任何第三方。请勿上传与工作无关的内容；建议沟通结束后 3 个月内清理。

- 与家长沟通录音的第三方同意，由教师在校外自行处理；本项目只在归档环节做提示，不代替学校规定。
- 提供「按日期批量清理音频」的入口（默认只清理音频，不动照片）。
- 提供「删除某学生全部音频」的入口（对应学生毕业或转出）。
- 照片与音频**不随导出外发**（只读快照的取舍见 `README` §6）。

# 第三部分 · 实施路线

## 原则

1. **界面尽量不变**：除作业提交率字段、宿舍容量入口、媒体附件三处（都是用户明确要求的），其余页面**只换数据源，不改交互**。任何必要的界面差异登记到「变更登记表」，随阶段交付一起给用户确认。
2. **旧应用只作对照，不作数据来源**：里面的数据是卖家的演示数据。改造期间真正需要带进新系统的只有会议里提到的 9 个学生，手工录入或 Excel 导入就行。旧应用留着，只为**逐页比对界面与行为**。
3. **口径先定后写**：出勤率、提交率、排名、占比、金额这五个口径，在写任何页面之前先写服务函数 + 单测，页面只是展示层。
4. **通用链路先验证再铺开**：先用 2–3 个最简单的 CRUD 页把「前端 → API → 库」的链路跑通，再动学生档案这种核心页。

## 阶段 2 · 主数据与高频页

| 风险 | 影响 | 对策 |
