## 通用改造规则（适用于所有 CRUD 型页面）

现有 20 多个页面都建立在 `renderCrudPage(cfg)` 这一个工厂上，改造时统一按下面这套替换，**页面级 `cfg` 契约保持不变**：

| 层 | 现状 | 改造后 |
|---|---|---|
| 数据读取 | `DB.table(k)` 同步读全局对象 | `GET /api/v1/<table>` 异步，带 `q/sort/dir/page/filter` 参数（服务端分页与排序） |
| 新增/编辑 | `openForm` 提交时直接 `DB.update/DB.add` | `PATCH/POST /api/v1/<table>[/{id}]` |
| 删除 | `DB.remove` | `DELETE /api/v1/<table>/{id}` |
| 批量 | 前端 `_sel` Set + 循环改 `DB.data` | `POST /api/v1/<table>/batch`（一次事务） |
| 字段定义 | 前端 `cfg.columns/fields` 硬编码 | 仍在前端 `cfg`，但 **`GET /api/v1/<table>/schema` 可覆盖**（为后续「用户自定义字段」留口） |
| 统计/KPI | 前端遍历全表算 | 服务端算，`GET /api/v1/<table>/stats`（**同一口径只实现一次**，消除 01 文档 §7.3 的口径不一致） |
| 导入 | 前端 SheetJS 解析 + 逐条写、无事务 | `POST /api/v1/transfer/import`（后端解析、**预览 + 冲突报告**、提交走单事务） |
| 导出 | 前端生成 xlsx | `GET /api/v1/transfer/export/<table>.xlsx`（导出当前筛选结果） |
| 渲染 | `render()` 返回 HTML 字符串 + `bind` 绑事件 | **不变**（保留现有写法，仅把取数改为 `await`） |
| 错误 | 异常进全局兜底 → `出错了：…` | 后端返回 `{code, message, detail}`；前端按错误码给中文提示与修复建议 |

**待办（全表通用）**：

1. 所有按姓名关联改为按 `student_id`；`name` 作为冗余展示列保留。
2. **所有班级范围内的表加 `class_id`**（用户已确认要支持多班：班主任带一个班，任课教师常教多个班）。只有一个班时前端无感，界面不出现班级切换器。
3. ~~接口按登录用户可见班级过滤~~ —— **已取消**：暂不做账号体系，单实例单用户。班级维度仍保留，只用于组织数据与统计分组（见 `05` §1、§7）。

见 `03` 的数据模型与 `05` 的班级维度设计。

## 一、概览

### 1. 工作台首页 `home`（`:6945`）

- **现状**：只读聚合 15 张表做 KPI 与卡片；可写 `appearance.quickActs`（14 项快捷操作启用与排序）、`appearance.todoCards`（今日待办卡片配置）、`countdowns` 表、`cdHidden` 根键。`computeFollowups()`（`:7584`）用硬编码紧急度权重（缺勤未联系 95、违纪未结案 80、待联系家长 72、生日/考试 65、谈话回访 60、助学金 55、欠费 50、待办 40）排序取前 14 条。

- **频率线索**：`争议`。

## 二、学生管理

### 3. 学生档案 `students`（`:9584`）★核心

- **现状**：主表 `students`；支持 CRUD、导入导出、批量、字段管理（`:9098` 增删改排序字段、显示位置、可搜索/可筛选、下拉选项、Excel 表头别名，存于 `meta.studentProfile`）、列表/卡片视图；详情页可**点任意字段内联编辑**（`:8738`），照片上传限 8 MB 并压到 240px；身份证输入自动推出生日期/性别/户籍地并提示校验位（`:9488`）；一键「记违纪/发起谈话/记大事记」预填姓名。学生档案页聚合 12 张表的记录（「一生一档」区块注册表 `STUDENT_ARCHIVE_BLOCKS`，`:8804`）。
- **问题**：① 默认学号 `'2024'+(人数+1)` 与 `meta.year` 不一致（`:9470`）；② 默认值有偏：性别男 / 住校 / 共青团员；③ `validate` 只查学号重复，身份证、手机号无校验；④ **删除学生无级联清理** → `seats/cadres/youth/duty/contacts` 留孤儿；⑤ 字段筛选项与列顺序在保存字段后被 `buildStudentCfg()` 重写，`defaultSort` 硬编码为学号升序；⑥ 详情页内联编辑直接落库，无并发保护（同一台机器多标签页会互相覆盖）。
- **改造后**：
  - 后端：`students` 表 + `student_field_defs`（字段定义，支持用户自定义）+ `students.extra` JSON 列存自定义字段值；`sno` 设唯一约束；`GET /api/v1/students/{id}/archive` 一次返回「一生一档」全部关联数据（避免前端 12 次请求）；删除学生改为**软删除 + 关联处理策略**（默认保留关联记录但标注「已删除学生」，可选级联清理）。
  - 校验：身份证校验位、手机号格式、学号唯一性、出生日期合法性一律后端校验并返回字段级错误。
  - 前端：字段管理 UI 保留，改为读写后端字段定义接口。
- **频率线索**：`高频`。会议明确指出**录入效率是首要瓶颈**（当天只录了 9 人 / 40 人），且数据来源是「多张纸表 + 电子表格，字段重叠但不一致、电话可能陈旧或手写、有重名」。→ **导入是需要重点设计的功能**（字段映射、唯一标识、同名消歧、冲突提示、人工确认），不能做成「一键导入」。

### 4. 班委成员 `cadres`（`:9648`）

- **现状**：`cadres` CRUD + 导入导出 + 卡片/列表；`sno/phone` 由 `beforeSave` 从学生表回填；`defaults.term = meta.year`；详情可跳学生档案。
- **问题**：无任期起止日期、无一人多职约束、`appraise`（考核）是 4 档手选无口径、按姓名关联。
- **改造后**：加 `startDate/endDate`（任期）；改为 `student_id` 关联；一人多职允许但**列表按学生聚合显示**；考核档位与「学期」绑定。
- **频率线索**：`高频`（班委名单要拍照发给任课老师）。

### 5. 团员名册 `youth`（`:11295`）

- **现状**：`youth` CRUD + 导入导出；KPI 可筛已缴/未缴；团员占比 = 团员记录数 / 全班人数（`:11281`）；团支部名写死 `meta.grade+meta.classNo+'团支部'`。
- **问题**：占比未按学号去重；`fee` 只有「已缴/未缴」无金额、无缴费时间/学期；与学生档案的 `politics==='共青团员'` **无一致性校验**，两处可互相矛盾。
- **改造后**：占比去重；缴费改 `{状态, 金额, 缴费日期, 学期}`；**与学生档案 `politics` 字段做双向一致性校验**（不一致时给出「以哪边为准」的确认，而不是静默矛盾）；团支部名改为 `meta` 可配字段。
- **频率线索**：`争议`（需求方列举时提到班委与团员，技术方归入可延后）。

### 6. 家长通讯 `parents`（`:13361`）

- **现状**：一行 = 一个学生的家庭联系（父/母姓名、电话、工作单位、监护人、地址、微信、备注）；卡片视图 + 监护人筛选；`beforeSave` 回填 `sno`。
- **问题**：**没有唯一性校验**，同一学生可建多条；以**姓名**为主键（`nameOptions`，`:3912`），重名学生直接错配；`guardian` 选项两处硬编码重复。
- **改造后**：`student_id` 唯一约束（一个学生一条主记录，多位监护人作为**子表** `guardians` 存，支持任意数量与优先级）；电话号码格式校验 + **陈旧号码标记**（会议明确提到电话可能已失效/手写错误）；按姓名/学号/电话/学生姓名模糊搜索。
- **频率线索**：`高频`。会议中班主任特别强调「家长通讯录」是最重要的功能之一，因为学生只写了一个联系人，联系不上时需要找其他监护人，「统一起来方便查找、直接搜名字就能打电话」。

### 7. 待办任务 `todos`（`:7744`）

- **现状**：`todos`（内容/截止/优先级/完成/备注）纯 CRUD + 导入导出；`done !== '已完成'` 的记录自动进首页跟进（`:7630`）。

- **改造后**：加 `分类/负责人/关联学生（可选）`；完成状态后端统一枚举；首页跟进的规则改为服务端计算。
- **频率线索**：`高频`（会议把「待办」明确列进第一版建议范围）。

### 8. 班规制度 `rules`（`:9716`）

- **现状**：`rules`（类别/标题/内容/更新日期）CRUD + 导入导出；类别固定 8 项硬编码；`beforeTable` 只做类别计数提示。
- **问题**：无版本号、无生效日期、**与违纪处理不关联**（违纪记录不引用班规条款）。
- **改造后**：加 `版本/生效日期/失效日期`；违纪记录增加可选 `rule_id` 引用，使「依哪条班规处理」可追溯。类别改为可配置。
- **频率线索**：`争议`。

### 9. 出勤记录 `attendance`（`:10144`）★口径重点

- **现状**：`attendance`（日期/姓名/学号/类型/时段/原因/是否联系家长）；支持全班点名弹窗（`:9946`，会按当天名单批量写记录）、复制家长电话、生成通知话术、KPI 按类型筛选。**统计口径**（`:9852`）：缺席 = 当天 `病假/事假/旷课` 的**记录条数**（迟到/早退不计），出勤率 = `(全班人数 − 缺席条数)/全班人数`，全班 0 人时返回 100%。
- **问题**：① 口径不统一（看板 KPI 计 5 类；首页跟进只认未处理的；档案按 5 类分别计数）；② 按记录条数而非去重学生数，一人一天两条会重复扣减；③ 无记录日也算 100%，分母固定为全班人数而非当日应到；④ 点名只清理当天 4 类（**早退不清理**，`:10056`），与新数据并存；⑤ 点名自动写 `handled:''` → 生成即进「缺勤未联系家长」跟进，属噪声；⑥ `period` 选项与全局 `PERIODS` 是两套硬编码。
- **改造后**：出勤率由后端单一服务函数产出：**缺席 = 当天去重后的缺席学生数**，分母 = 当日应到人数（考虑请假/休学等状态，若无状态字段则等于全班人数），**迟到/早退单独成指标不混入缺席率**；点名接口改为「按日期整体提交」（一次事务覆盖当天记录，含全部 5 类），杜绝残留；`period` 统一取全局常量；`handled` 区分「已通知/无需联系/待联系」三态，点名生成时默认「无需联系」，不再污染跟进列表。
- **频率线索**：`高频`（会议明确列为第一版建议范围）。

### 10. 座位安排 `seats`（`:11005`）

- **现状**：`seats`（行/列/姓名/组/备注）+ `seatPlan`（行列数、排位原则文本）；三视图（网格/图标/列表）；支持拖拽排座与「点选源→点目标」、调整行列、**每月换座**（整体环移）、**一键随机排位**、编辑排位原则、打印座位表。
- **问题**：① **没有任何自动算法考虑性别、身高、视力、成绩或「互助搭配」**——「排位原则」只是展示文本，与轮换行为无关；② 随机排位**清空备注**（视力/身高等关键信息丢失）；③ `shiftSeats` 整体替换无撤销；④ 手工新增/编辑**不校验行列冲突**，会造出「座位消失」的重复格（后写覆盖）；⑤ `plan.cols` 可以为 0。
- **改造后**：座位数据模型保留 `row/col`，但后端加**唯一约束 (row, col)** 与冲突校验；随机排位**保留备注**（并新增「锁定座位不参与随机」标记）；所有批量操作（随机/轮换/交换）在服务端一次事务完成，并返回变更摘要供撤销（服务端保存上一次快照，支持一键回退）；「排位原则」改为真正的规则配置（可选：不指定性别混排、按身高排序、视力优先前排、成绩互助搭配），先在**服务端实现为可选的排序策略**，默认仍为纯随机以复刻现状。
- **频率线索**：`延后候选`（会议明确把「座位」列入下一阶段）。但需求方手动排座目前靠纸质，属于会实际使用的功能。
- **备注**：现实现的随机排位会丢备注，是**数据丢失级缺陷**，建议无论优先级都先修。

### 11. 值日安排 `duty`（`:11175`）

- **现状**：`duty`（星期/组/区域/组长/检查/成员）CRUD + 导入导出；概览卡按周一~周五分组；`area` 固定 8 项；`members` 是顿号分隔自由文本。
- **问题**：① **不存在轮换逻辑**（全脚本只有静态 weekday 排布）；② 概览卡只渲染周一~周五，周六/日值日在概览中不可见；③ `members` 是自由文本，不与学生档案关联，**无法统计个人值日次数**；④ `check` 手填无日期，无法回答「本周卫生几次待改进」。
- **改造后**：`members` 改为关联学生（可多选），从而支持「个人值日次数」统计；`check` 改为带日期的检查记录子表；每周次生成实例（`duty_instance`：日期 + 组 + 成员 + 检查结果），即可支持「今天谁值日」和轮换追溯；概览覆盖全周。
- **频率线索**：`高频`（会议列为第一版建议范围中的「值日或作业中的一两个模块」）。

### 12. 宿舍分布 `dorms`（`:13619`）★用户痛点 1

- **现状**：一行 = **一个床位分配**（楼栋/房号/床号/姓名/学号/是否寝室长/备注）；卡片与列表双视图；动作含新增床位、点空格子加人（预填床号）、房间底部「增添住宿生」、**行内改容量**（点「✎ N人间」）、点床位看详情/编辑/删除、导入导出、打印。
- **问题**：01 文档 §7.1/§7.2 已逐条列出，核心是四条 —— 容量寄存在「数组顺序第一条记录」上且种子数据里**根本没有这个字段**（于是全部回退 8 人间）；改容量用 `window.prompt()`（exe/CEF 下常抛异常）；分组键 `building|room` 字符串拼接，未命中时**仍然提示成功**；床号是自由文本（「1号床」/「1」/「01」/「靠窗」），解析后重复或为 0 → 满员误判、记录从视图消失。
- **改造后**（详见 `04`）：
  - 数据模型拆成 `dorm_room`（楼栋 / 房号 / **容量** / 备注，`(building, room)` 唯一）+ `dorm_bed`（房间 + 床位号，`(room_id, bed_no)` 唯一 + 学生 `student_id`）。
  - 容量是房间的正式字段，`NOT NULL DEFAULT 8`，通过**应用内模态框**修改（替换 `prompt()`），不再有「设置成功但没生效」。
  - 床位号改为整数，界面显示「N 号床」；导入时归一化（提取数字），无法解析的行**进入冲突报告**而不是静默丢进 extra 区。
  - 所有查询按 id（房间 id / 床位 id），不再用字符串拼分组键。

## 八、设置

### 33. 设置与数据 `settings`（`:16693`，`noNav:true`）

- **现状**：班级信息（`:17097`）、身份切换（科任/班主任，`:17111`）、外观（头像/标题/夜间/背景色/背景图/蒙版）、导出含软件+数据的 HTML（`:17257`）、导出 JSON（`:17273`）、从 JSON 恢复（整对象替换 `DB.data`，`:17299`）、恢复示范数据（`:17311`）、清空业务数据（保留 meta+appearance，`:17617`）、本地文件模式（File System Access）、IndexedDB 自动备份 5 份（`:17315`）、exe 专属数据目录与自动备份（`:17329`）。
- **问题**：① 存储占用按 5 MB 估算（`:16711`）；② 恢复 JSON 只校验 `obj.students` 存在，**不校验各表结构**（`:17291`）；③ 清空数据只清 `SEED_DATA` 里存在的键，运行时懒建的表被整体丢弃；④ 散落多个 localStorage 辅助键（`wb_lastBackup`、`bzr_autobackup`、`bzr_last_export`）；⑤ 身份切换只影响侧栏可见性，`go()` 不做守卫，深链可绕过。
- **改造后**：
  - 存储占用改为**真实读取数据目录大小**（数据库 + 媒体分项），不再按 5 MB 估算。
  - **备份功能推迟**（`05` §4）：界面只说明「数据目录在哪、怎么整包拷走」，不做自动备份、不做加密、不做恢复界面。
  - **访问保护不做**，也**没有身份与可见性**（`05` §1）；不要为它预留接口。
  - 清空数据改为服务端操作，对**所有已知表**生效，并在执行前提示一次（防误触）。
  - 页面可见性（`pageVisibility`）保留为本机偏好，不再与角色挂钩。
- **频率线索**：`高频`（备份是会议三大待办之一：本地备份已有数据、明确高频功能、设计本地持久化与迁移）。

## 九、跨模块的统一需求（本次梳理的汇总）

1. **学生主数据统一**：所有模块的「姓名」关联改为 `student_id`；学籍号 `sno` 为唯一业务键；同名消歧在录入与导入时统一处理。会议明确「转写/录入效率是首要瓶颈」「电话号码可能陈旧、手写或错误、有重名」。
2. **统计口径唯一化**：出勤率、作业提交率、成绩排名与及格线、团员占比、助学金金额 —— 每项只保留**一处**实现（后端服务层），前端只展示。
3. **媒体留档统一**：照片与录音统一走媒体库，不再 base64 入库；沟通类记录（家长联系、家访、谈话、班会、班级活动、大事记、矛盾调解）均可挂附件。
4. **错误处理统一**：后端返回结构化错误（错误码 + 中文说明 + 修复建议），前端不再出现「出错了：Cannot read properties of undefined」这类提示。
5. **导入统一**：全部走后端「解析 → 预览 → 冲突报告 → 人工确认 → 单事务提交」，不再有绕过校验的「清空并替换」。
6. **数据导入与迁移**：**这是基础设施，要做好** —— 手工录入、Excel/CSV 导入（表头别名匹配、逐行校验、预览、冲突报告、单事务、幂等）、旧应用 JSON 导入通路。**旧应用里那批演示数据本身不迁**（见 `03` §8）。备份仍推迟（`05` §4），本轮只保证「数据目录可整包拷走」。
7. **删除策略统一**：软删除 + 关联处理（默认保留关联并标注），避免孤儿记录。
