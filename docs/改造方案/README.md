# 班主任工作台改造方案

> 对象：`raw-material/web-app/班主任工作台.html`（买来的单文件网页应用，18995 行 / 4.1 MB）
> 依据：对该应用的逐行逆向（本次会话完成）+ `.validation/context_repair/meeting_analysis.md`（班主任需求访谈分析）

---

## 1. 目标与范围

本轮解决三件事：

1. **持久化**：数据从浏览器缓存（localStorage 单键 `bzr_workbench_v1`）搬到本地后端 + 本地数据库，脱离浏览器配额与「关掉页面就可能丢」的风险。
2. **复刻**：现有 **33 个页面**的功能逐项保留，逻辑从「前端直读直改全局数据对象」改为「前端调后端 API」，界面与交互尽量不变。
3. **三处确定调整**（用户已知的真实痛点，本文档已定位根因）：
   - 宿舍分布配置时出现**意义不明的报错**；
   - 作业**提交率目前靠用户手填**，疑似应自动算；
   - 需要**导入照片与录音**做沟通留档。

**本轮范围之外**（不是现有功能，属于新增能力，本轮不做）：公网访问、OCR 批量建档、多校/学校级汇总、自然语言录入、自动排班类智能算法。（**内网访问与手机端在范围内**，见下。）

**关于范围的一处决定**：会议分析曾建议「先验证高频功能，不按现有工作台全量复刻」，用户已确认那只是**当时技术方的建议** —— 实际使用中用户能把全部功能都用上，因此**本轮按全量功能实施，不做减法**。会议识别出的**使用频率线索**仍逐页保留在 `02-需求梳理-逐功能.md`，用途改为**实施排序参考**（先做高频页，让试运行期更早可用），不再作为删减功能的依据。

**用户已确认的决定**（推翻了本文档早期版本的若干假设，完整说明与四轮变更记录见 `05-部署与访问设计.md`）：

1. **是一个项目，不是 HTML**：交付一个完整项目。
2. **每位老师自己单独部署一份**，和学校无关；老师自己就是管理员。
3. **不做账号、也不做访问口令** —— 用户已决定「裸奔，有需求了再说」（风险记录见 `05` §2）。
4. **手机与电脑通过内网地址访问**：服务跑在某台机器上，手机连同一局域网即可用。
5. **手机端奔着好用做**：全部 33 个页面都要适配，不是只保关键页。
6. **支持多个班**：班主任带一个班，任课教师常教多个班。
7. **录音只归档**：不通过本项目录音，老师自己用手机打电话时录，录完上传归档。
8. **跑在老师自己的电脑上**（不再用学校的 32 位 Win7）→ Python 用 3.11，技术选型不受 32 位限制。
9. **部署环境不联网**（客户要求）→ **运行期不得访问任何外网**，依赖必须预先离线打包带走。不做 HTTPS。
10. **部署打包与备份推迟**：本轮先让项目在开发机上跑起来；一键启动包与备份功能后面单独做。

## 2. 技术路线（结论）

| 项 | 选择 | 理由 |
|---|---|---|
| 项目形态 | 一个**前后端完整项目**：后端服务 + 前端静态资源 + 数据库 + 媒体目录 | 用户已确认「不再是一个 HTML」 |
| 部署形态 | 服务跑在**老师自己的电脑**上，监听内网端口；**手机或电脑用浏览器访问**。一键启动包推迟 | 部署打包「后面再说」（见 `05` §4） |
| 使用者与账号 | **单实例单用户**：无账号、无角色、**无访问口令** | 用户已决定「裸奔」；风险已记录在 `05` §2 |
| 班级维度 | 数据模型支持多个班（`class` 表 + 各表 `class_id`） | 班主任带一个班，任课教师常教多个班 |
| 后端 | **Python 3.11** + FastAPI + SQLAlchemy 2.0 + SQLite（WAL） | 与团队现有 `.validation/conda` 环境一致；目标机是老师自己的电脑（`05` §5.1） |
| 数据存储 | 那台电脑上的单个 SQLite 文件 + `media/` 媒体目录；**备份推迟**，靠整目录拷贝 | 单文件便于整包拷走；本轮不做备份功能 |
| 前端 | 保留现有原生 JS 技术栈，拆成 ES 模块（无构建步骤），**全页面移动端适配**，遵守**主流现代浏览器基线** | 33 页都是「配置对象 + 渲染函数」，可近乎 1:1 迁到模块文件；换框架等于全部重写 |
| 媒体与录音 | 照片上传 + 音频**归档**（不做页内录音） | 录音由老师用手机自行完成，见 `04` §3 |
| 文件组织 | 后端按「模型 / 服务 / 路由」三层拆分；前端按「core / components / pages」拆分；**单文件硬上限 600 行** | 直接回应用户要求：不能出现几千上万行的单文件 |
| 网络与隐私 | **运行期完全不联网**（客户要求服务器不联网）：零埋点、无 CDN、无云调用、无自动更新；删除授权层；数据不离开那台电脑 | 未成年人及家长信息不经过任何第三方 |

前端保留原生栈的关键依据：现应用的数据层与渲染层是「同步直读直写全局单例」模式，`renderCrudPage(cfg)` 一个工厂就撑起了 20 多个模块页。改造时把这层换成 `api.js` + 一个异步的 `crudPage(cfg)`，配置对象 `cfg` 的契约基本可以沿用 —— 这是工作量最小、回归风险最低的路径。

## 3. 三个已知痛点的结论

### 3.1 宿舍分布配置报错

**根因已定位（4 条，按可能性排序）**：

1. `班主任工作台.html:13824` 点「✎ N人间」改容量时调用 `window.prompt()`。该应用有 exe 外壳（`window.__BZR_EXE`），CEF/Electron 环境常**禁用或直接抛异常**于 `prompt()`，异常被全局兜底捕获后弹出 `出错了：…` 这类无上下文提示。这是「意义不明报错」最可能的来源（**此条为推断，实机未复现；验证方法与另三条已确认的根因见 `04-重点改造与实施路线.md` §1.1**）。
2. `:13861`、`:13611` 按 id 查找记录后**不判空直接取属性**（`DB.find(...)` 未命中返回 `undefined`），一旦记录被删或 dataset 为空串，就抛 `Cannot read properties of undefined`。
3. `:13830-13845` 容量只写在该房间**数组顺序第一条**记录上，且分组键用 `building|room` 字符串拼接；拼接含 `|` 或 `undefined` 时目标找不到，**却仍然提示「已设置成功」**——容量静默回退，用户看到「设置了没生效」。
4. 种子数据里 `dorms` **根本没有 `capacity` 字段**，容量取值逻辑 `Number(x.capacity) || 8` 于是全部回退 8 人间；用户设过的容量在重开后"消失"。

**改造方案**：把宿舍从「一条记录=一个床位、容量寄生在记录上」改为 `dorm_room`（楼栋/房号/容量）+ `dorm_bed`（床位分配）两张表，容量是房间的正式字段；用应用自带的模态框替换 `prompt()`；所有查找路径返回结构化错误（错误码 + 中文说明），不再有裸异常进兜底。详见 `04-重点改造与实施路线.md`。

### 3.2 作业提交率

**结论：当前确实是用户手填的，代码里没有任何自动计算。**

- `rate` 是普通数字字段（`:11919`），新增时**默认 100**（`:11929`），列表按它出进度条、按科目求平均、低于 90 告警 —— 全部读的是手填值。
- 同一张表里还有一份自由文本 `unsubmitted`（未交名单，顿号分隔），只被用来生成「欠交频次榜」和学生档案里的欠交次数（`:8826`、`:11949`），**两份信息互不相通、无一致性校验**。
- 首页「作业待收」卡片读的是 `h.submitted` / `h.total` 字段（`:7011`），而这两个字段**全文件不存在**，所以该卡片恒显示 0。
- 另有一份重复数据源：`courses[].homework[]` 里也有 `rate`（`:14689`），与 `homework` 表并行存储。

**改造方案**：`total`（应交人数）与 `unsubmitted`（未交名单，改为关联学生）成为正式字段，`rate` 改为**后端计算**（`(total − 未交人数) / total`），保留一个「手动覆盖」开关以备特殊场景；同时合并两份作业数据源，修好首页待收卡片。

### 3.3 照片与录音留档

**现状**：只有图片，且全部以 base64 data URL 塞进那一个 localStorage 键（头像 240px、多图 1200px、JPEG 0.82）；**全应用不存在录音能力**（无 `MediaRecorder`、无 `getUserMedia`）；设置页的存储占用条按 5 MB 估算，早已是隐患。另有字段错配：种子数据里 `meetings.photo` / `events.photo` 是空字符串，而班会页实际写的是 `images` 字段 —— 老数据里的照片接不过来。

**改造方案**：新增媒体库 —— 文件落盘到 `data/media/年/月/`，数据库只存元数据（归属对象、类型、文件名、大小、尺寸、时长）；图片生成缩略图，录音在页内直接播放；沟通留档（谈话/家长联系/家访/班会/班级活动/大事记）支持「照片 + 录音」混合附件。后续可接本地 FunASR 做录音转写（团队已有该环境），属后续增强项，不在本轮。

## 4. 与会议记录的对照

| 会议结论 | 本方案的处理 |
|---|---|
| 第一阶段本地单机部署，不做公网/手机访问 | **部分更新**：仍然是「每人一份、自己部署」，但**手机/电脑通过内网地址访问**；公网仍不做（见 `05`） |
| 不能只用浏览器缓存，需要本地持久化 | 采纳。SQLite + 媒体目录，都在老师自己的机器上 |
| 保留现有工作台导出结果，后续导入新系统 | **采纳**：把导入与迁移做成**基础设施**（Excel/CSV 导入 + 旧 JSON 导入通路）；但旧应用里那批**演示数据本身不迁**（`03` §8） |
| 先验证高频功能，不按现有工作台全量复刻 | **不采纳，已确认全量实现**。用户反馈实际使用中全部功能都会用到；会议的高频线索改为**实施排序参考**（先做高频页） |
| 需要学生唯一标识（学籍号优先），同名人工确认 | 采纳，作为数据模型的第一原则：按姓名关联改为按 `student_id`；学籍号 `sno` 为唯一业务键（多班下改为 `(class_id, sno)` 唯一） |
| 本地不等于安全终点，需备份加密、删除策略 | **本轮不采纳**：用户已决定不做备份、不做访问口令（风险已知情接受，见 `05` §2）。数据只在本地，靠整目录拷贝兜底 |
| 尚未检查该工作台的源码或网络请求，不能断言是否上传数据 | **已补做**：逆向确认无埋点、无业务数据外传。唯一公网调用是课程表 OCR 的 tesseract.js CDN（`:11643`），授权激活会往腾讯云函数发激活码 + 本机指纹（`:18489`）。改造后：前者改为默认关闭 / 按需加载（失败给明确提示），后者整体删除 |
| 多人使用可考虑每人独立本地部署 | **采纳**：每位老师自己部署一份，互不互通，和学校无关（见 `05` §1） |
