## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  使用者：老师本人（单实例单用户，无账号体系）                    │
│  手机浏览器 或 电脑浏览器  →  http://<老师电脑的内网地址>:<端口> │
└───────────────┬──────────────────────────────────────────────┘
                │  局域网（不出公网）
┌───────────────▼──────────────────────────────────────────────┐
│  后端  FastAPI + Uvicorn，跑在老师自己的电脑上，监听内网地址     │
│                                                              │
│  api/v1/   ← HTTP 层：参数校验、错误码、序列化                    │
│  services/ ← 业务规则层：统计口径、床位分配、提交率、导入映射     │
│  models/   ← 数据层：SQLAlchemy 模型（含 class）                │
│  storage/  ← 文件层：数据目录、媒体落盘                        │
│                                                              │
│  同时静态托管前端（frontend/），手机与电脑共用同一份             │
└───────────────┬──────────────────────────────────────────────┘
                │ SQLite (WAL) + 媒体文件
┌───────────────▼──────────────────────────────────────────────┐
│  数据目录（机器上的本地目录）                                   │
│    workbench.sqlite      业务库                                │
│    media/2026/09/….jpg   照片原件                              │
│    media/2026/09/….m4a   音频归档（老师手机录音后上传）           │
│    media/thumbs/….jpg    缩略图                                │
│    logs/app.log          操作日志                              │
└──────────────────────────────────────────────────────────────┘
```

**没有桌面外壳、没有账号体系、也没有访问口令。** 现行模型是「每位老师自己部署一份、单用户使用」：服务跑在**老师自己的电脑**上 → 老师用手机或电脑通过内网地址访问。**部署环境默认离线（客户要求服务器不联网）→ 运行期零外网依赖**，详见 `05` §5.2。早期版本里的「校内共享服务 + 账号与权限」「可选访问口令」「按 32 位 Win7 适配」都已作废，完整说明与六轮变更记录见 `05-部署与访问设计.md`。

> **一键启动包与备份功能已推迟到后续阶段**（见 `05` §4）。本轮目标是「能在开发机上跑起来、功能完整、**不联网可用**」。

**关键分工原则**

| 职责 | 归属 | 理由 |
|---|---|---|
| 统计口径（出勤率、提交率、排名、占比、金额合计） | 后端 `services/` | 现状同一业务最多有 4 套算法（见 `01` §7.3），必须收敛到一处 |
| 校验（学号唯一、床位冲突、状态机、格式） | 后端，前端做即时反馈 | 前端校验可被绕过（现状的「清空并替换」导入就是例子） |
| 局域网内无访问控制 | **不做**（用户已决定「裸奔」） | 风险已记录在 `05` §2，不作为本轮实现内容，也不再讨论 |
| 界面状态（搜索词、排序、当前页、选中集、展开状态） | 前端 `store.js` | 与持久数据无关，不该进库也不该发请求 |
| 渲染（HTML 字符串拼接、事件绑定） | 前端，**保留现有写法** | 现有 33 页全是这个模式，改造成本最低 |
| 文件（照片 / 音频归档 / 备份） | 后端 `storage/` | 现状 base64 进 localStorage 是配额爆炸的根因 |

## 2. 技术选型

### 2.1 选定方案（已确认）

| 层 | 选型 | 版本约束 |
|---|---|---|
| 运行时 | Python | **3.11** —— 目标机是老师自己的电脑（`05` §5.1），与团队现有 `.validation/conda` 环境一致 |
| Web 框架 | FastAPI + Uvicorn | FastAPI ≥0.115 |
| 运行方式 | 本轮：开发服务器（`uvicorn`）监听内网端口；**一键启动包推迟** | 用户已确认「部署的事后面再说」，见 `05` §4 |
| ORM | SQLAlchemy 2.0（同步 Session）+ Alembic 迁移 | 同步足够：单用户，写操作稀疏 |
| 数据库 | SQLite，开启 WAL、`foreign_keys=ON`、`busy_timeout=5000` | 单文件便于整包拷贝；WAL 支持手机与电脑并发读 |
| 访问保护 | **不做**（无账号、无口令） | 用户已决定「裸奔」，风险记录见 `05` §2 |
| 校验/序列化 | Pydantic v2 | 与 FastAPI 同源 |
| Excel/CSV | openpyxl（读写 xlsx）+ 自写 CSV 解码（UTF-8 → GBK 回退，沿用现逻辑） | 替代前端 SheetJS |
| 图片 | Pillow（缩略图、EXIF 方向、格式归一化） | 纯本地库，离线可用 |
| 音频 | mutagen 或 ffprobe（读时长、采样率、编码） | 只读元数据，**不做转码**；手机录音常见 `m4a` / `amr` |
| 日志 | 标准库 logging + 轮转文件 | 本机排障用；内容需脱敏（`05` §6） |
| 测试 | pytest + httpx（API 测试） + SQLite 内存库 | |
| 前端 | 原生 ES Modules + 原生 CSS + **全页面移动端适配**，遵守**主流现代浏览器基线** | 无构建步骤；手机与电脑共用同一份；基线见 `05` §5.3 |

### 2.2 不采用的方案（备查）

- **Node 技术栈**（Fastify + better-sqlite3 + exceljs + sharp）：**已排除**。它唯一的优势是与现有 exe 外壳（Electron）同栈、便于合并打包；选 Python 的理由是团队已有 3.11 环境可直接复用、本地方案与生态更成熟。
- **含构建步骤的前端**（Vite + Vue 3）：暂不采用。仅在后续要长期演进 UI、或页面数继续增长时才重新评估 —— 33 个页面全部重写一遍的收益，抵不上回归风险与工期。

> 后端技术栈已确定为 Python（见 §2.1），不再是待确认事项。

**分层禁令**（写进 `CONTRIBUTING`，评审时执行）：

1. `api/` 里**不允许写 SQL**，也不允许写业务规则；只做「取参 → 调 service → 返回 schema」。
2. `services/` 里**不允许 import FastAPI**，保证可独立单测。
3. `models/` 里**不允许写查询逻辑**，只定义表与关系。
4. 统计口径函数**只允许有一处实现**；若第二处需要，必须改成调用第一处。

**（前三条已有测试守着：`backend/tests/test_layering.py`。）**

### 3.1 实际落地与上面这份设计稿的差异（阶段 5 收口时逐条对齐）

上面两棵树是**设计稿**（写在动手之前），落地时按「一个概念一个文件、超 600 行就拆」
调整过。差异如下，读完这一段就不必拿设计稿去猜文件名：

| 设计稿 | 实际 | 为什么 |
|---|---|---|
| `api/deps.py` | `api/session.py` + `api/committing_route.py` | 会话依赖与「写请求在响应前提交」是两件事，后者要 `route_class` 才覆盖得住全部接口 |
| `api/v1/students.py` | `api/v1/student_fields.py` + `student_reports.py` | 字段管理（增删字段）与档案聚合（一生一档、评语、同名报告）是两条路 |
| `api/v1/homework.py` | 无 | 提交率**写入时就算好**（钩子里），不需要「重算」入口 |
| `api/v1/courses.py` | `courses.py` | 落地了，但课程从「嵌套结构」改成四张平表（`02` §23、`06` 96–105） |
| `services/dorm_alloc.py` / `duty_roster.py` | `dorm_service.py` + `dorm_duty_service.py` | 床位分配与值日生成是两个聚合 |
| `services/followups.py` | `analytics_service.py` | 跟进清单与看板聚合读同一批数据，拆开反而要互调 |
| `services/student_identity.py` | `roster.py` | 姓名→学生、班级人数、名单解析都是一件事：**「老师写的名字怎么变成 id」** |
| `services/import_map.py` | `import_service.py` + `table_io.py` | 一边是导入流程（预览/冲突/事务），一边是表格读写（xlsx/CSV/别名） |
| `services/fee_calc.py` / `comment_draft.py` | `fee_service.py` / `comment_service.py` | 与上面同名的模块合成一个服务文件（都不足 300 行） |
| `storage/paths.py` / `size_report.py` | 并入 `config.py` 与 `media_store.py` | 目录布局只有一处用得到，单独成文件反而要来回跳 |
| — | `services/class_scope.py`、`hooks.py`、`params.py`、`money.py`、`student_fields.py`、`table_write.py`、`table_query.py`、`field_value.py`、`course_service.py`、`course_stats.py`… | 设计稿没预见到「同一规则在多处实现」会那么频繁，这些是**收敛出来**的单一实现点（钩子、参数解析、金额单位、写入管线、班级归属…） |

前端同理：`styles/` 实际是 5 个分层文件（`tokens / base / layout / components / pages`）——
设计稿里的「一组件一文件」没落地，因为样式按层分文件更少的来回跳；
`pages/` 是**扁平的** `pages/xxx.js`（一个文件一个页面定义，没有每页一个目录）。

### 4.2 移动端适配规则（手机与电脑共用同一份前端）

## 6. 数据库设计

### 6.1 四条设计原则（会议记录 + 用户确认）

1. **学生唯一标识优先用学籍号**：`student.sno` 加唯一约束；所有关联表用 `student_id` 外键，`name` 仅作冗余展示列（便于导出与阅读）。
2. **同名必须人工确认**：迁移与导入时，无法通过 `sno` 匹配的姓名进入冲突报告，绝不自动猜。
3. **班级维度从一开始就存在**：所有班级范围内的表带 `class_id`；`student` 的唯一约束是 **`(class_id, sno)`** 而不是全局 `sno`。用户已确认要支持多班（班主任带一个班，任课教师常教多个班），完整设计见 `05` §5。
4. **未成年人及监护人信息最小化**：**内网可达但不出公网**；数据与媒体都留在本机，不经过学校服务器或任何第三方；**不依赖任何外部服务**（无 CDN、无云调用）。本轮**不做访问口令、也不做备份** —— 这是用户已知情并接受的决定，风险记录见 `05` §2；提供按学生、按日期的媒体清理入口。完整措施见 `05` §6。

### 6.2 表清单（约 35 张）

| 分组 | 表 | 要点 |

## 7. 单文件行数约束（用户明确要求）

**硬规则**：

1. 单文件 **≤ 600 行**（含注释空行）。超过即拆，不接受例外。
2. 目标值：后端单文件 ≤ 400 行，前端单文件 ≤ 300 行，页面目录内文件 ≤ 500 行。
3. **自动检查**：`tools/check_file_size.py` 遍历 `backend/app` 与 `frontend/src`，超过阈值即非零退出；接入提交前钩子与 CI。
4. 拆分手法固定为三种，优先级从高到低：
   - **按职责分**：路由 / 服务 / 模型 / 序列化 分离（后端）；渲染 / 配置 / 事件处理 分离（前端）。
   - **按子功能分**：一个页面目录下的多个子模块各一文件（如学生档案的 `detail.js` 与 `fields-admin.js`）。
   - **按聚合分**：一张表或一组紧密相关的表一个模型文件。
5. **禁止**：为了压行数把多段逻辑塞进一行、把常量内联进函数、用 `eval` 拼装、把文件拆成语义不明的 `utils2.js`。行数上限是问题信号，不是目的。
6. 对照参考：现状单文件 18995 行、单段脚本最长约 5800 行，改造后同一功能域的代码应落在 **3–8 个文件、每个 ≤ 400 行**的规模。

## 8. 数据导入与迁移（基础设施，要做）

**先说边界**：旧应用里内置的是卖家的**演示数据（假的）**，那批数据本身**不需要迁移**。但**导入与迁移这件事本身是项目的基础设施** —— 真实数据迟早要进来（老师手里可能还有零散记录、以后每学期都有新数据、也可能换系统），所以要按下面的标准做扎实，不能糊。

### 8.1 核心：日常导入基础设施（必做）

这是最重要的一条路径 —— 会议里明确说**录入效率是首要瓶颈**（当时手动录 40 人只录进去 9 个）：

- 后端解析 Excel / CSV（xlsx 走 openpyxl；CSV 兼容 UTF-8 与 GBK）；
- **表头别名匹配**（沿用并扩充旧应用的 `FIELD_SYNONYMS` 思路），两遍匹配：精确 → 包含；
- **逐行校验 + 冲突报告**：必填缺失、学号重复、姓名对不上、日期非法、电话格式可疑；
- **预览 → 人工确认 → 单事务提交**，失败整体回滚。**绝不允许「清空并替换」绕过校验** —— 旧应用 `:5222` 就是这么翻车的；
- **幂等**：同一份文件重复导入不产生重复记录；
- 每个表都提供「下载导入模板」入口。

### 8.2 旧应用 JSON 导入（保留这条通路）

基础设施建好后，把旧应用的导出 JSON 接进来是顺手的事，而且有两个理由必须保留：

1. 老师那 9 条真实数据可以整体搬过来，比手抄可靠；
2. 万一将来发现旧应用里还有别的真实数据，不用临时补工具。

设计仍是 **只读旧 JSON、只写新库，绝不修改原始文件**，并**复用 §8.1 的校验与冲突报告**，不另造一套。

```
tools/migrate_legacy/
├── run.py                  # 入口：--input 旧JSON --output 新数据目录 --report 报告目录
├── read_legacy.py          # 解析旧 JSON，兼容各版本字段缺失
├── resolve_students.py     # 姓名 → student_id 解析（sno 优先 → 姓名+班级 → 冲突报告）
├── map_tables.py           # 各表字段映射（一表一函数，见 §6.3）
├── extract_media.py        # data URL → 媒体文件落盘 + media 记录
└── report.py               # 生成迁移报告（markdown + csv）
```

流程：旧应用「设置 → 导出 JSON」→ 运行工具 → 产出报告 → 人工处理冲突 → 再跑一次（幂等，每次生成全新库）→ 验证 → 切换。

**必查清单**（逐项给出条数）：

1. **同名/姓名无法唯一匹配**的记录（学号缺失或冲突）。
2. **重复床位**：同房间床号解析后重复的记录。
3. **宿舍容量**：每个房间推断出的容量与来源（用户设置值 / 默认 8），需人工确认。
4. **作业口径**：`rate` 与 `unsubmitted` 名单推算值不一致的记录（列出两个值供确认）。
5. **`courses[].homework`**：并入主表时标注来源，避免重复计数。
6. **成绩**：`scores.scores` 缺失科目、总分与逐科求和不一致的记录；`exams` 日期倒序的记录。
7. **媒体**：data URL 解码失败的图片（列出 id 与所属表）。
8. **孤儿关联**：关联到不存在学生的记录（`seats` / `cadres` / `youth` / `duty` / `contacts`）。
9. **日期异常**：未来日期、空日期、格式非法的记录。
10. **旧数据中的真实个人信息**：报告中**打码展示**（姓名只显示姓 + `*`），提醒用户数据敏感性。

### 9.3 安全与隐私（简化版）

| 项 | 措施 |
|---|---|
| 网络暴露 | 服务在局域网内可达，**不出公网、不做端口映射**。注意：同网段任何人都能访问 |
| 访问保护 | **不做**（无账号、无口令）—— 用户已知情并接受，风险记录见 `05` §2 |
| 数据位置 | 数据、媒体、日志都在**本机**，不经过学校服务器或任何第三方 |
| 传输 | 局域网 HTTP 明文，不做 HTTPS |
| 外网依赖 | **运行期零外网依赖**（客户要求部署服务器不联网）：零埋点、无 CDN、无外部字体/图标、无云调用、无自动更新、无远程授权。启动后拔掉网线，全部功能照常 |
| 依赖交付 | 目标机器不能 `pip install` → 在联网的开发机上预先 `pip download` / `pip wheel` 拉全量依赖，随项目交付（`05` §5.2） |
| 授权层 | 删除；不再有任何远程激活调用（它本来就要联网，留不了） |
| OCR | **默认关闭**：原方案依赖公网 CDN（tesseract.js `:11643`），离线环境不可用。界面要明确写「此功能需要联网，当前环境不可用」，既不静默失败也不报错吓人 |
| 备份 | **本轮不做**。唯一手段：数据目录可整包拷走（`05` §3）；「清空数据」前提示一次 |
| 媒体 | 照片与音频（老师手机录制后上传归档）与业务数据同权限；删除进回收站而非物理删除；提供「按日期清理」与「按学生清理」 |
| 删除策略 | 学生软删除 + 显式选择关联处理方式；提供「彻底删除某学生全部数据」的入口 |
| 日志 | 只记操作类型与记录 id，**不记姓名、电话、身份证、媒体路径** |
